### Priority policy

- **P0 (launch blocker):** Credentials, authorization, funds, integrity and idempotency, or exploit path.
- **P1 (core paid-course launch):** Actual acquisition → purchase → entitlement → watch → support, plus safe deployments.

## Phase 0 — Security containment and integrity (P0, must complete before collecting payments)

- [ ] **P0-01 Rotate/revoke exposed credentials immediately.** `src/lib/csr.server.ts` contains a private Vapi token fallback; `src/lib/cloudinary.server.ts` contains a Cloudinary API secret fallback; `src/lib/auth/preview.ts` contains an embedded preview OAuth client secret. Consider all committed values compromised. Rotate/revoke at each provider; replace with runtime-only env/secret-manager inputs; eliminate literal secret fallbacks and `.env` file scraping; scan all Git history, logs and deploy artifacts; assess usage. Public Firebase web config and public Vapi keys are not private secrets by themselves. **Done when:** revoked keys fail, new keys are only in deployment secrets, automated secret scan passes, and provider logs have been reviewed.
- [ ] **P0-02 Enforce RTDB authorization.** `rget/rput/rpatch/rdel` in `firebase.server.ts`, `studio.server.ts`, `csr.server.ts`, `community.server.ts` call `*.json` without a Firebase user token or server Admin credential. First export current Firebase rules and test deny-by-default behavior in emulator. Move privileged operations to Firebase Admin SDK with scoped server credentials (or migrate them to transactional Postgres); lock public/client access to financial, auth, user, admin, CSR and moderation nodes; test cross-user read/write denial. **Done when:** anonymous and non-owner direct REST requests cannot read/write protected nodes, while verified server requests work. **Do not infer current live rules from repo**—they are not present.
- [ ] **P0-03 Fix moderator privilege escalation.** `moderatorOrBootstrap()` in `src/lib/studio.server.ts` assigns moderator to the first active member if the list is empty. Remove visitor-triggered bootstrap; seed approved admin UID/role via privileged admin-only migration; enforce server-side role checks on every moderation, settlement, catalog, payout and revenue action. **Done when:** a newly registered user can never become moderator, including on an empty database.
- [ ] **P0-04 Replace email-only superuser gate.** `src/lib/master.ts` compares email to a hardcoded address; `masterAccess`, `issueActivationCode`, `listPayoutRequests`, `markPayoutPaid` rely on this check. Use verified stable Firebase UID + custom claims/DB role, enforce verified email and MFA for administrators, log all privileged actions, introduce two-person/dual review for high-value payouts. **Done when:** email display alone never conveys admin authority.
- [ ] **P0-05 Eliminate activation / referral race conditions.** `redeemActivationCode` checks then modifies the activation code across several independent requests; `activateMembership` credits referrals and records a payment before completing membership state. Implement transactional single-use code claim, membership entitlement and referral event; idempotency key per redemption; compensate/reconcile partial failures. **Done when:** 100 concurrent attempts on one code produce exactly one membership redemption and one eligible commission.
- [ ] **P0-06 Implement correct financial accounting.** `postLedger`, `requestPayout`, `markPayoutPaid` and `confirmOrder` write different RTDB paths without one atomic commit; `payout_${Date.now()}` is not collision-proof and `markPayoutPaid` debits before marking paid. Prefer Neon/Postgres for immutable double-entry ledger, serializable transactions/row locking, unique event/idempotency constraints and reconciliation jobs; keep display balances derived from ledger rather than editable counters. **Done when:** concurrent withdrawals, payment retries, refund retries, server crashes and partial failures cannot change balance incorrectly.
- [ ] **P0-07 Gate membership on actual settled payment.** `src/routes/checkout.tsx` accepts a manually issued activation code; `activateMembership` inserts a payment record with `gateway: "sponsor"` without a PSP capture/settlement check. Integrate an eligible Philippine checkout provider for cards/GCash/Maya; verify webhook signatures, capture status and amount server-side; persist orders and payment intents; issue entitlement exactly once on `paid` event; build refund/chargeback reversal; keep manually issued codes as a deliberately separate admin-sponsored flow with audit trail. **Done when:** a client cannot activate membership or receive a referral commission from an unpaid, failed, reversed or forged payment.
- [ ] **P0-08 Secure existing sessions and auth architecture.** `src/lib/session.ts` persists Firebase ID + refresh tokens in `localStorage`. Use secure HttpOnly/SameSite session cookies or another documented XSS-resilient session pattern, CSRF checks, refresh/revocation, device logout, MFA for admin, and security headers. Choose **one app membership identity authority** (currently Firebase Auth) and remove/deactivate unused Grok/Better Auth preview hooks for production. **Done when:** production sessions are revocable, isolated, and not exposed to ordinary page JS.
- [ ] **P0-09 Protect arbitrary file/media exposure.** `src/routes/api/media/$id.ts` serves uploads without auth and with `cache-control: public`; `readUploadedVideo` reads base64 from RTDB. Introduce owner/public visibility, authorization, MIME/size limits, malware/content checks, abuse throttling, CDN object storage and signed time-limited URLs. **Done when:** private files cannot be read by guessed or shared unauthenticated URLs.
- [ ] **P0-10 Security abuse controls.** Apply rate limits, quotas, request validation and origin/CSRF protection on sign-up, login, activation, payout, media upload, AI generation, Vapi assistant creation, comments, click tracking and public CSR endpoints. Prevent user-controlled provider spending. **Done when:** abusive bursts are rejected predictably and API costs have enforceable per-user limits.

## Recommended implementation sequence (do not parallelize money features before security)

1. **Release 0 — Contain:** P0-01 through P0-04, deny unsafe database access, disable privileged money features until audited. All provider credentials rotated.
2. **Release 1 — Transactions:** P0-05 through P0-10. A single transactional order → payment → entitlement → ledger flow, with replay protection and negative tests.
3. **Release 2 — Core paid course:** P1-01 through P1-09, P1-11 and P1-12. A paid member can buy and watch a properly protected lesson with stable progress.
4. **Release 3 — Hardening:** P1-10, P1-13, P1-14, P2-09, P2-11. Staging sign-off and production smoke verification.
5. **Release 4 — Expansion:** P2-01 through P2-08, each gated by real merchant, publishing, livestream, AI or Vapi integrations.
6. **Release 5 — Growth:** P2-10, P3-01 only after instrumentation proves core acquisition and retention.

## Launch acceptance gates (all mandatory for paid production)

- [ ] **Secrets:** No active private tokens in source/current Git history, shipped artifacts, source maps, server logs or public API responses. Revoked credentials no longer authorize calls.
- [ ] **Authorization:** Anonymous, inactive, other-member and non-admin actors are denied every protected server/RTDB/streaming path.
- [ ] **Money:** Successful verified payment gives exactly one entitlement; failed/forged/refunded payment cannot create usable access or spendable reward.
- [ ] **Concurrency:** 100 parallel redemptions and 100 concurrent payout attempts preserve ledger invariants. Duplicate webhooks are idempotent.
- [ ] **Course:** Admin publishes a lesson, member buys, protected video plays, progress persists across devices, refund revokes entitlement.
- [ ] **Operational:** Staging passes typecheck, lint, tests, build, e2e, secret scans, smoke checks and restore drill; logs and alerts cover all critical service paths.
- [ ] **Product integrity:** Every UI action has a real backend effect; disconnected integrations are unmistakably disabled, never labeled 'posted' or 'paid' without proof.
- [ ] **Rollback:** Previous app version can redeploy safely without orphaning orders, credits, media or memberships.

## Implementation conventions for engineering agents

1. Keep current UI/route design intact unless a security issue demands a change; refactor behind stable interfaces.
2. Do not put any real passwords, keys, tokens, personal user data, payout account numbers or secrets in commits, issues, screenshots, PRs or test fixtures.
3. Complete tasks one vertical slice at a time; add/adjust unit, integration and E2E tests with each feature.
4. Treat a source-code plan, stubbed queue, or provider placeholder as **NOT DONE**. Only mark complete with reproducible tests and live/sandbox proof.
5. Create feature branches/PRs with precise migration impact, acceptance evidence, rollback steps and operator notes.
6. Before touching financial production data: back up data and inspect current provider configurations/rules. Never guess live secrets, payment status or previously posted transactions.

### Known verification limits

This audit inspected the committed source/tree through the GitHub connector. It **did not** inspect Firebase RTDB rules, live provider dashboards, Vercel env variables, existing data, live billing credentials, deployed domain health, or execute the app's tests/build. Findings about absent provider integrations are based on the inspected implementation; environmental configuration must be verified during each task. Do not treat the items as already fixed.
